1. Selected organisation: OwoRail

OwoRail is a simulated Lagos-based digital-wallet operator. Customers hold naira wallets, send money to each other, pay merchants and billers by app, USSD or web, and are charged small fees. It is an integrity-critical transaction-processing system: money must never be created, lost or posted twice.

  • Users: customers (through the payments application), merchants, support agents, compliance (KYC) analysts, fraud and finance analysts, internal auditors, and the DBA.
  • Data: customers and their phones, KYC profiles in three tiers, wallets (customer, merchant and system), merchants and billers, fee rules, transactions, a double-entry ledger, status history, reversals and an audit log. Money is stored as integer kobo, times in UTC, and all data is synthetic.
  • Key operations: onboard a customer; transfer; pay a merchant or bill; charge fees; reverse a transaction; wallet statement; reconcile balances against the ledger; velocity (fraud) check; monthly merchant settlement.

1 Design and modelling Requirements and 18 business rules; a Chen ER diagram; 13 relations normalised to BCNF; a PostgreSQL 16 implementation with 94 named constraints, a deferred balanced-ledger trigger, append-only tables, posting and reversal functions, and least-privilege roles. 120 constraint, 40 procedure and 41 role tests passed, plus 13 consistency checks. A catalogue check confirms the database matches the design document. Rebuilding the normalisation sample by joining the tables gives back the original report, so the decomposition is lossless.
2 Query optimisation 1.1 million synthetic transactions; nine queries from real operations measured with EXPLAIN (ANALYZE, BUFFERS) before and after composite and covering indexes, a better statistics target, a materialised view and rewrites. Settlement 1,778 → 3.6 ms; daily-limit check 3.2 → 0.05 ms; dormant-wallet query over 30 s → 133 ms (NOT IN → NOT EXISTS); reconciliation 2× faster after fixing the distinct-count estimate. The costs are reported too: index space 252 → 560 MB, posting 16 % slower, and one index the planner never used.
3 Transactions and concurrency Python scripts that drive several real sessions in a fixed order: commit, rollback, savepoints, crash durability, every isolation level, lost update, row locks, deadlock, and the posting function under load. 49 checks passed. A transfer survived a server kill (WAL recovery). Write skew was stopped only by SERIALIZABLE. Deadlocks: 100 of 200 with unordered locking, 0 with ordered. No overspending, no double posting of duplicate requests, and a FEES-wallet hot spot measured.
4 NoSQL (MongoDB) A document model loaded from the same PostgreSQL data (ledger lines and history embedded); $jsonSchema validators; indexes measured with explain(); multi-document transactions; key-value, wide-column and graph models also discussed. 58 checks passed, and every query returns the same rows as PostgreSQL. The statement query reads exactly 20 documents with one index, but full reconciliation takes 31 s against 0.8 s in PostgreSQL. The conclusion is polyglot persistence: PostgreSQL for money, MongoDB as the read model.
5 Distributed and cloud A three-node replica set and a sharded cluster (config server, two shards, router); a distribution and deployment design for OwoRail. 25 checks passed. Failover paused writes for 11.4 s and lost no acknowledged majority write. A w:1 write was rolled back after a failover. A hashed wallet shard key split the data 50/50, while a time key sent all new writes to one shard. The ledger favours consistency under partition (CAP), and the data is hosted in Nigeria (NDPA 2023).

4. Individual technical reflection

Design choices. Integer kobo and a double-entry ledger made "are the books right?" a query, and that query confirmed correct balances after a bulk load of 1.1 million transactions, hundreds of concurrent postings and a server crash. I enforced the rules in the database itself (named constraints, a deferred trigger, posting only through functions), so a test can see which rule refused a bad row. I kept PostgreSQL as the system of record because the measurements, not preference, showed MongoDB's weaknesses for money: slow whole-ledger aggregation, no foreign keys, and conflicts instead of waiting.

Challenges. Removing the time from ledger lines was right for 2NF, but it made the statement query need a rewrite in Portfolio 2. A design decision came back in three later portfolios. The planner was only as good as its statistics (32,000 estimated wallets against 102,000 real ones caused a spill to disk), and a partial index that was faster when forced was never chosen. Laptop timings varied 2–3×, so I compared buffers and documents examined. Some results looked right and weren't: a failover "with no outage", and a "partition" made with docker pause that delivered the writes anyway.

Lessons. Measure before deciding, and measure the right thing. Every index, copy and replica has a cost. Consistency is a setting chosen per operation: with w:1 an acknowledged payment can disappear. Tests should check outcomes (which constraint, identical rows), not only that nothing failed. Next, I would simulate KYC daily limits in the data, test on separate machines, split the FEES wallet and feed MongoDB by change data capture. The full reflection is in docs/reflection.md.
